# 상대 이동 지연 대응 — 2026-11-06

사용자는 상대 이동이 약1초 늦게 보인다고 보고했다. 사용자 기기의 RTT/FPS 실측은 아직 없어 원인을 확정하지 않는다. 기존 상대 위치는 최신 서버 위치를 지수 보간했고 수신 경과 시간이나 전송 지연을 고려하지 않았다.

## 변경

- 최신 두 서버 위치와 tick 차이로 상대 수평 속도를 추정한다. 수신 이후 경과 시간과 측정된 입력 확인 왕복 시간의 절반을 반영하되, 최대150ms만 앞서 표시한다. 최대 달리기 속도 초과·텔레포트·사망·부활·연결 중단은 속도 추정을 버린다. 300ms 이상 상태가 없으면 예측을 멈추고 마지막 서버 위치를 사용한다. 공통 벽 충돌을 유지한다.
- 상대 보간 강도를18에서35로 높여 부드러움 때문에 추가되는 표시 지연을 줄인다. 서버가 판정하는 상대 피격 위치를 수정하지 않는다.
- 입력seq의 실제 전송~서버확인 시간으로 통신 지연을 측정한다. 브라우저 단일 clock을 사용해 시계 차이를 배제하며, 같은ack 중복 표본은 제외한다. HUD에 통신ms, 300ms 초과 안내, 상태500ms 초과 수신 지연을 표시한다. 이는 순수 네트워크ping과 달리 서버 갱신 대기도 포함한 값이다.
- 송신 버퍼64KiB 이상이면 새 입력을 쌓지 않는다. 오래된 입력이 계속 밀리는 것을 방지한다.
- 기존 방은 전 세계 공통 Lobby DO가 처음 접근하면서 로비 서버 근처에 배치될 수 있었다. 새 방의 최초 reserve에 방장 실제 접속 대륙 기반 locationHint를 전달한다. 클라이언트의 임의 헤더를 제거하고 Worker request.cf.continent로만 생성한다. AS→apac, OC→oc, NA→wnam, SA→sam, EU→weur, AF→afr. 기존 방을 옮기거나 매칭 상대 범위를 제한하지 않는다. 힌트는 최선 노력이며 정확한 위치나 지연 감소를 보장하지 않는다. 별도 서비스·유료요금제를 추가하지 않는다. 지역 선택값은 방 DB에 저장하지 않는다.

Cloudflare 공식 데이터 위치 자료: https://developers.cloudflare.com/durable-objects/reference/data-location/ (공식 cloudflare/cloudflare-docs 원문 확인). DO는 최초 생성 위치를 유지하며 locationHint는 첫 get에만 적용되므로, 서버 수정 배포 후 새 방으로 확인해야 한다.

## 제한과 검증

상대의 다음 입력은 도착 전에 알 수 없으므로1초 지연을 무제한 예측하지 않는다. 피해/탄약/승패는 계속 서버가 확정한다. 과거 위치로 총격을 판정하는 지연 보상은 아직 도입하지 않았다. 적용 한도와 엄폐 뒤 피격 공정성 규칙은 별도 결정이 필요하다.

추가 검사4개: 입력확인 지연/수신정지 측정,150ms 예측 상한과 정지, 부활/순간 이동 예측 초기화, 실제 Worker/Lobby에서 trusted 배치힌트 전달 및 임의헤더 제거. 전체61개 자동 검사·웹빌드·Worker dry-run·모바일 DOM 검증. 실제 두기기 지연 개선 여부는 별도 확인한다.
