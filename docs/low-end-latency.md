# 저사양 렌더링·온라인 입력/서버 시간 최적화 — 2026-11-08

사용자는 저사양 기기의 낮은 FPS와 기기 간 온라인 지연을 줄이고 서버 판정을 정확하고 빠르게 반영하도록 요청했다. 새 유료 서비스나 피해·이동 속도·승리·보급 규칙은 도입하지 않는다.

## 그래픽과 CPU

낮음 화질은 픽셀 비율 상한0.6, 그림자 패스와 선택적 반사/별/광원 장식을 생략한다. 건물·문·층·엄폐물·캐릭터와 실제 충돌은 유지한다. 높음·균형으로 돌아가면 저장된 그림자 선택을 복구한다. 자동 화질은 모바일 초기 상한1.0(기존1.5), 지속28FPS 미만에서 최저0.5까지 낮추며0.85 이하에서 저사양 프로필을 적용한다. 느린 프레임2초 판정·복구6초 창은 유지하여 한 번의 로딩 프레임으로 품질을 바꾸지 않는다. 수동 높음/균형은 자동으로 바꾸지 않는다. 맵 전환에도 현재 프로필을 적용한다.

봇의 시야와 발사 시 장애물 검사는 렌더 삼각형 광선 조회 대신 서버와 같은 문/층/엄폐물 충돌 상자를 사용한다. 발사 벽 충돌점과 법선도 유지한다. 게임이 별도로 사격 판정하므로 Babylon의 자동 pointer move/down/up picking을 끈다. 무기 획득·장비/난이도/선택창의 반복 DOM 갱신은20Hz로 줄이고 조준·이동·물리·피격/탄약 UI는 기존 흐름을 유지한다.

동일 클라우드 Node/NullEngine, 같은 장면과 측정 스크립트에서 봇3마리 업데이트 중앙값6.44ms→0.47ms(각90회, 준비5회), p95 11.48ms→3.94ms를 기록했다. 이는 CPU 구간 측정이며 실제 휴대폰 FPS·발열·전체 CPU/GPU 사용률이나 개선률이 아니다. 재현은 `node docs/qa/performance-bench.mjs`이며 전후 원시 결과는 작업 환경 QA 폴더에 둔다.

같은844×390 해상도의 실제 Chromium 장면에서 균형 대비 저사양 프로필의 프레임당 드로 제출 수338→152(약55% 감소), 활성 메시157→152를 확인했다. 렌더 해상도를 바꾸지 않은 비교이며 드로 제출 수 감소가 같은 비율의 실기기 FPS 증가를 의미하지 않는다. 재현은 `node docs/qa/render-cost.mjs`이다.

## 입력·전송

입력 heartbeat를 render loop와 분리한25ms 타이머에서50ms 간격으로 전송한다. 화면 루프도 같은 스케줄러를 호출하므로 중복 전송하지 않는다. 조작 이벤트 뒤 microtask로 긴급 전송하며 최소16ms 제한을 둬 서버의 초당80패킷 제한 안에 둔다. 점프/대시는 다음 로컬 예측 프레임에도 전달한다. 전송 실패 시 아직 보내지 못한 일회성 행동을 유지하되, 연결 종료/메뉴/화면 비활성 중에는 지우고 재접속 후 오래된 사격을 재실행하지 않는다. pagehide에서 타이머를 정리하고 pageshow에서 다시 시작한다.

5FPS로 main callback을 제한한 실제 Chromium 게임 초기화/시뮬레이션 검사에서1.2초 동안 화면 업데이트5회, 입력22개(이동21개)를 확인했다. 프레임이 낮아도 사격이 서버 탄약에 반영됐으며 메뉴를 열면 중립 입력, 낮음 설정 시 그림자 비활성화를 확인했다. 이 검사는 렌더 함수를 대체하므로 GPU나 실제 저사양 기기의 긴 메인스레드 정지를 재현한 성능 수용 검사가 아니다. 메인스레드 자체가 멈추거나 무선망이 지연되면 타이머·네트워크도 늦어질 수 있다.

protocol2 hello를 보낸 클라이언트에는 공통 공개 플레이어 정보와 해당 수신자만 필요한 인벤토리·탄약·장비·입력 ACK를 합쳐 보낸다. 공통 JSON은 tick당 한 번만 직렬화하고 개인 부분만 덧붙인다. 구형 클라이언트/서버는 기존 전체 스냅샷으로 계속 호환한다. 공식 전적/서버 저장 체크포인트는 원래 전체 상태를 사용한다. 참가 여부·닉네임·건강·팀·점수·이벤트와 공통 보급은 유지한다.

로컬 Worker 실제 개인전20명·팀전20명, 각19명 protocol2와1명 구형을 섞은 검사에서 패킷 약14.8~15.0KB→8.3~8.5KB(약43% 감소), 서버19.9~20.5tick/s, 입력 ACK 중앙값47~49ms를 확인했다. 같은 클라우드의 로컬 값이며 실제 인터넷 RTT를 뜻하지 않는다.

## 서버 정확성

서버의 seq ACK는 수신만으로 증가시키지 않고 실제 tick에서 처리·폐기한 명령까지 갱신한다. 수신 큐의 마지막seq도 확인해 중복/역순 명령은 거부한다. 클라이언트가 이미 적용됐다고 오해해 예측 명령을 먼저 버리는 문제를 막는다.

50ms 고정 tick의 실제 시간 누락을 누산한다. 보통150ms 지연은3tick으로 따라잡으며 큰 정지는 최대250ms/5tick까지만 계산한다. 따라잡는 동안의 사격·폭발 이벤트를 모아 한 번에 보내 중간 이벤트를 잃지 않는다. 입력 TTL은 운영 Worker의 신뢰할 수 있는 Date.now 기준300ms이며 클라이언트가 보낸 시각은 신뢰하지 않는다. 서버가 오래 멈춘 뒤 오래된 이동/사격을 재생하지 않는다. 사망 중에 받은 일회성 명령도 폐기하여 부활 직후 예전 방아쇠가 자동 실행되지 않게 한다. 이 동작 역시 수정 전 탄약12→11의 실패를 확인하고 수정했다. 입력을 많이 보내도 이동 시간·사격 간격·피해·탄약은 계속 서버가 제한한다. 과거 시각의 명중을 임의 인정하거나 무제한 지연 보상은 추가하지 않는다.

상대 예측은 기존 최대150ms 지평에서 멈추며 패킷이300ms 늦었다는 이유로 원래 위치로 뒤로 튀지 않는다. 다음 서버 위치에 따라 기존 보정으로 수렴한다. 실제 벽·문 충돌은 계속 적용한다.

## 검사와 남은 확인

수정 전 ACK 조기확정·시간 누락·전송량·그림자 패스·AI 삼각형 조회5개가 기대 동작으로 실패했다. 별도로 서버 정지 후 오래된 입력과 패킷 지연 시 역방향 스냅2개 실패를 확인한 뒤 수정했다. 단순 모듈 로딩 오류를 Red로 기록하지 않는다. Worker 테스트 런타임에는 신규 import를 연결했다. 낮아진 해상도 하한에서 더 긴 회복 시간이 필요하므로 회복 검사의 실행 창을 늘렸다.

전체 자동243개/69파일, PC/모바일 DOM, 타입/웹 프로덕션 빌드, Worker dry-run, 실제20인 소켓/구형 혼합 프로토콜,5FPS 입력 분리 브라우저 검사를 통과했다. 네트워크 재현은 `node docs/qa/network-load.mjs`(기본Worker8791, 허용Origin5173), `ONLINE_BASE`로 공개 서버도 검사할 수 있다.5FPS 검사는 `node docs/qa/low-end-browser.cjs`(Vite5185, 허용Origin5185의 별도 Worker8793/독립 persist 폴더 필요)이다.

실제 저사양 Android/iPhone의 지속 FPS·발열·메모리·서로 다른 무선망/거리에서의 판정 체감은 별도 확인이 필요하다. 특정 기기의60FPS 또는 지연 제거를 보장하지 않는다.
