# TDD 작업 기준

사용자는2026-11-06부터 TDD로 개발하도록 요청했다. 이후 기능 개발과 동작 변경 버그 수정에 적용한다.

1. 요구 동작과 완료 조건을 정한다. 미정 게임 규칙은 기존 승인 절차를 따른다.
2. 해당 동작을 재현하는 테스트를 먼저 추가하고 실행한다. 구현 부재 또는 기존 버그 때문에 의도한 단언이 실패하는지 확인한다(Red). 의존성/경로/문법 오류는 이 단계의 완료가 아니다.
3. 테스트를 통과시키는 최소 코드를 구현한다(Green).
4. 테스트를 유지하며 구조를 정리한다(Refactor). 관련 회귀 검사와 변경에 필요한 빌드·공개 서비스 검증을 수행한다.
5. 작업 기록에 요구 동작, 먼저 실패한 검사와 실패 이유, 변경 내용, 통과 결과 및 실기기 미확인 사항을 기록한다.

동작을 검증하고 구현 내부를 그대로 복제하는 테스트는 피한다. 테스트 통과를 위해 수용 조건을 약화하지 않는다. 실제 네트워크 입력/시간/연결 문제는 가상 시간 회귀 검사와 공개 서버 통합 검사를 구분한다. 그래픽·터치·FPS·통신 체감은 자동 검사만으로 완료를 선언하지 않는다.

문서 정리처럼 실행 동작이 바뀌지 않는 작업에는 별도 테스트를 만들지 않는다. 테스트 가능한 정상 코드를 일부러 변경해 실패를 꾸미지 않는다. 기존64개 검사는 유지하며 과거 테스트 작성 순서를 TDD였다고 소급하지 않는다.

예: 상대 재접속 기한 버그를 수정할 때 먼저 ‘두 명이 끊긴 뒤 한 명만 복귀해도 원래30초 기한에 종료’ 검사로 실패를 재현하고, 수정 후 같은 검사를 통과시킨다. 기존에 수정이 끝난 이 사례를 새로 수행한 것으로 보고하지 않는다.
